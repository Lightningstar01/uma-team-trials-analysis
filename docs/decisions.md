# Decisions

This file holds two things only: decisions/rationale not already reflected as current state in `CLAUDE.md`, `roadmap.md`, or `team-trials-reference.md`, and every open question across the project. If something is settled and stated as fact elsewhere, it doesn't belong here.

## Decisions

- An earlier Ace-adjustment approach — dividing an Ace's score by 1.1 — was tried and removed, superseded by the Advanced Mode contribution-score formula (Phase 2) in `roadmap.md`. It didn't work because the Ace Bonus gets diluted by whatever Opponent Rating and Streak rates apply that match; see `team-trials-reference.md`'s Score Details section for why.
- The MVP ships Simple Mode only (raw averages); Advanced Mode (`S = I + T`) is Phase 2. The standalone Ace-adjustment formula (`Gained Score × (M − 0.10) / M`) that the roadmap once listed for Advanced Mode was dropped, because dividing each match's score down to base score in `S = I + T` already removes the Ace bonus.
- Ace slot input (Edit Team parsing and the potential-uma database) and per-match Ace flags moved from the MVP to Phase 2, since Advanced Mode is their only user.
- Support Cards are out of scope: the app doesn't model them. The Support rate is account-wide and identical for every uma; Simple Mode ignores it, and Advanced Mode takes it as a player-entered input.
- Advanced Mode assumes the player always picks the Top Option when choosing opponents. Chosen because it matches the developer's own play pattern, and lets the Opponent Rating Bonus be computed from Team Rating alone via the empirical curve (originally from one manually entered average-opponent-rating input) instead of tracking per-match opponent choice.
- Streak Bonus isn't modeled in Advanced Mode (Simple Mode uses raw scores). Its effect is small next to Opponent Rating, which dominates — judged negligible for now.
- Aptitude bonuses/penalties on Team Rating (S/A/B/F–G rank modifiers — see `team-trials-reference.md`'s Team Rating section) are not modeled. The app treats Team Rating as the flat sum of the 15 umas' individual Ratings. The site will carry a disclaimer noting this simplification and reminding players that an S-rank in either of the two relevant aptitudes (surface, distance) for a race category is worth a 2% bonus each.
- In Advanced Mode (Phase 2), Team Rating is entered manually by the player rather than derived by the app from uma RANK badges.
- **Contribution-score formula (`S = I + T`), base score:** `I` is built from each match's base score (Gained Score divided by the full multiplier) rather than raw or Ace-adjusted Gained Score, so history stays comparable when Team Rating or Support rate changed between matches, and Ace, Support, and Opponent Rating effects are isolated. Every uma is compared as a non-Ace; the player supplies which umas are Aces.
- **Contribution-score formula, `I` at the reduced multiplier:** `I = average base × (1 + Mopp_without + Support)`, and `T` covers all 15 umas including the uma itself. This way the slice of the uma's own score that comes from the multiplier its Rating earns is counted only in `T`, never twice, and both terms are in real team points, so `S = I + T` equals the team's score drop if the uma were removed.
- **Contribution-score formula, removal:** the uma is removed entirely (no replacement baseline) so its value is the points it brings to the team.
- **Phase 2 contribution-score formula, `R'` definition:** `R' = R − (that uma's Rating)`, where Rating is the RANK-badge-derived value (see the Rating floor table in `team-trials-reference.md`), not the uma's average score.
- Team Rank floors (the developer-supplied table, E through UD9) were tried and dropped for modeling the opponent rating: the Top Option's rating does not follow them (e.g. at Team Rating 115,904 the top opponent, 125,153, was still below the next floor). The empirical curve in `team-trials-reference.md` replaces them. The floor table is kept in `team-trials-reference.md` as reference only.
- The empirical curve is assumed to continue beyond the sampled Team Ratings (65,493–335,567); the site will carry a disclaimer about the lack of data. Team Bonus is excluded from all calculations (it appears only on Score Details, not Score Info), and the site will carry a disclaimer for that too.
- Advanced Mode no longer asks for the average opponent rating, because typing it for every race is too much effort; the curve estimates it. The player enters Team Rating and Support rate once, is responsible for keeping them up to date, and each match snapshots the current values.
- Corrected an earlier reference-doc statement that `OpponentRatingRate` is the multiplier minus 1: the Score Details rows show the rate equals the multiplier (Super Creek 1st place: `10,000 × (1 + 0.10 + 1.6843 + 0.1069 + 0.02) = 29,112`).
- **Chunk 2 (OCR) UX:** uploading Score Info screenshots prefills the same `MatchEntryForm` 15-row grid (instead of prefilling from the previous match); the user reviews/edits inline with the exact same row UI and validation manual entry already uses. There's no separate OCR review screen and no separate fallback screen — if OCR fails or misreads a row, the grid is just left editable, which is manual entry's existing role.
- **Chunk 2 (OCR) upload validation is light:** reject non-image files and files over 15 MB; no crop/dimension requirements. Bad OCR reads are caught by the user during row review, the same way a typo would be.
- **Chunk 2 (OCR) extracted fields:** `umaName`, `distance`, and `points` only, per Score Info row. RANK badge, Ace status, and epithet banners are out of scope for this screen (Phase 2/Edit Team concerns) and are not extracted.
- **Chunk 2 (OCR) name extraction:** the uma name is isolated from a name+points line by each word's x-position (words with `bbox.x0` in the name column), not by stripping tokens (e.g. an "MVP" badge) from the line's raw text. Real OCR output showed portrait/badge art noise bleeding into nearly every row's text (not just an occasional MVP badge), which regex-stripping can't reliably isolate.
- **Chunk 2 (OCR) row detection:** rows are formed by pairing each name+points line with its nearest distance line (by vertical position, within a max-gap threshold) rather than clustering all lines into row "bands" by a fixed gap threshold. Real bbox output showed intra-row and inter-row vertical gaps overlap too much for sequential gap-clustering to reliably separate rows; anchor-line pairing only needs the two line types that matter and ignores all other noise regardless of its position.
- **Chunk 2 (OCR) split overlap row:** the real fixtures showed the Air Groove overlap row is cut incompletely in *both* screenshots — screenshot 1 has its name+points but not the distance pill (cut off at the bottom edge); screenshot 2's leading fragment for it didn't OCR into anything usable at all. So a name+points line with no nearby distance is still kept as a row (distance left null) instead of being dropped, and `mergeScreenshotRows` infers the missing distance by elimination: the roster always has exactly 3 umas per distance category (confirmed in `team-trials-reference.md`'s Match Structure section), so if exactly one row is missing a distance and exactly one category is short exactly one member, that's the answer. Anything less clear-cut (more than one row missing, or an ambiguous count) is left null and surfaced as a warning rather than guessed. Cross-screenshot text stitching (combining the two screenshots' fragments for the same row) was considered and rejected: it wouldn't have helped for the real fixtures anyway, since the leading fragment's distance text didn't OCR into anything recognizable that run.
- **Chunk 2 (OCR) distance-word matching:** a distance line is matched by finding a distance word as a whole token anywhere in a short (≤3-token) line, not by requiring the full trimmed line to equal the distance word exactly. A real OCR run produced `"y Mile"` for one row instead of `"Mile"` — an exact-line match missed it, which also broke the split-row elimination above (it needs exactly one row missing a distance to work).
- **Chunk 2 (OCR) fixture cleanup:** the original two real screenshots were renamed `Score_Info_1a.jpg`/`Score_Info_1b.jpg` (five more match pairs, `2a`/`2b` through `6a`/`6b`, were added alongside them) and now live only in `src/ocr/__fixtures__/`. The `docs/Score_Info_1.jpg`/`Score_Info_2.jpg` "source of truth" copies were deleted — nothing but a `CLAUDE.md` doc line ever referenced them, so keeping two copies in sync wasn't earning its cost.
- **Chunk 2 (OCR) split-row rescue via uma-name dictionary:** the missing-row bug above (a row vanishing when Tesseract splits its name and points across two OCR lines) is now actively fixed, not just warned about, for the common case. Added `src/ocr/umaNames.js` (developer-supplied list of known playable uma names, exact case-insensitive match only - not fuzzy) and used it in `parseScreenshotRows` to recognize a name-only line (no points, but its name-column text matches the dictionary) as an "orphan name," paired by vertical proximity with a nearby "orphan points" line (points present but no name-column words) using the same nearest-match pairing as name<->distance. Verified against the real fixtures: this recovered El Condor Pasa's row on `Score_Info_2a/2b.jpg` and Grass Wonder's row on `Score_Info_3a/3b.jpg`, both previously dropped entirely. One dictionary entry was corrected: the developer's list had "Machikane Tannhauser," but the rest of the app already uses the screenshot-confirmed "Matikanetannhauser" (one word) for that character, so the dictionary was updated to match rather than kept as two spellings for the same uma.
- **Chunk 2 (OCR) missing-row warning:** real end-to-end testing of the batch-upload change (below) against all 6 real fixture pairs found a row can silently vanish with no warning when Tesseract splits one visual row's name and points across two separate recognized lines (seen on `Score_Info_2a.jpg`/`2b.jpg`: El Condor Pasa's row was lost this way — the points landed on a line with no name-column words, and the name landed on a line whose leftover text didn't match `POINTS_REGEX`). `toOcrGridRows` already warned when OCR found *more* rows than `ROSTER_SIZE`; it now also warns on fewer, instead of silently padding the shortfall with blank rows.
- **Chunk 2 (OCR) leading-distance fragment:** re-tested the split-row distance pill against all 6 real fixture pairs (real Tesseract OCR, not synthetic fixtures) — it's legible in 2 of 6 pairs (as a standalone distance-word line sitting above the next screenshot's first full row) and unrecognizable noise in the other 4, so it's not reliable enough to replace elimination-based inference, only worth trying opportunistically first. Added `findLeadingDistance(lines)` to `parseScoreInfo.js`, which detects this fragment when present, and a third optional `mergeScreenshotRows(rowsA, rowsB, leadingDistanceForB)` argument that applies it — but only when exactly one merged row is still missing a distance, same ambiguity guard as elimination — before falling through to the existing `inferMissingDistances` elimination logic, which remains the primary/only mechanism for the other ~2/3 of cases.
- **Chunk 2 (OCR) row-correctness warnings:** added `validateRows` (`src/ocr/parseScoreInfo.js`), re-run against the live entry grid (manual or OCR-filled, on every render) rather than computed once at parse time, so a warning clears as soon as the user fixes the row. It flags a filled row whose name isn't in `umaNames.js`'s dictionary, a distance category with other than the fixed 3 members, or a score under 10,000 pts.
- **Chunk 2 (OCR) name auto-correction (supersedes "bad reads are caught during row review" above, for names specifically):** since the uma roster is a closed, known list, a name on a confirmed row (a name+points line, so it's known to be a real row) is now corrected to its closest dictionary match by edit distance (`resolveUmaName`/`closestUmaName` in `umaNames.js`) whenever it isn't an exact match, instead of being left as raw, possibly-garbled OCR text. This is what fixes half of the `Score_Info_3b.jpg` "Oguri Cap" misread from the Open Questions list ("Oguri Cap" → "guri Cap," edit distance 1). A correction still produces a "please verify" warning (`collectNameCorrectionWarnings`) naming the raw OCR text, since a closest-match guess is still a guess. The split-row rescue's name gate (`lookupUmaName`, exact-match only) is deliberately unchanged — it decides whether a name-only line is a real stray name at all (vs. badge/epithet noise landing in the same column), and fuzzy-matching that gate would start turning noise into spurious rows, unlike the name-correction case above where the row's existence is already confirmed by its points match.
- **Chunk 2 (OCR) points-split rescue:** the other half of that same `Score_Info_3b.jpg` misread turned out not to be a genuine misread at all — real Tesseract output showed Oguri Cap's row split into two lines, `"WHY ogu 42"` (a name fragment plus a bare `"42"` sitting exactly at the points column's x-position, but with no comma or "pts" suffix) and `"I guri Cap 711 pts"` on the very next line (12px away in y) — Tesseract had read the full "42,711" correctly, just split its two comma-groups across the row's two output lines the same way it sometimes splits name and points. Added detection for this shape (a bare 1-3 digit token in the points column with no "pts" suffix, paired by tight vertical proximity - see `MAX_POINTS_SPLIT_GAP` in `parseScoreInfo.js`) that reassembles the full number as `prefix + remainder.padStart(3, '0')`, restricted to candidates whose own points are still under 1,000 (a comma group after the first is always exactly 3 digits, so a bigger value was never missing a prefix). Verified against real OCR output from all 6 fixture pairs before implementing - this exact shape occurs once across all of them, so the fix is scoped to that confirmed pattern rather than guessed. Produces its own "please verify" warning (`collectPointsCorrectionWarnings`), same reasoning as the name correction above. This does not cover every possible truncation - if Tesseract genuinely fails to read a digit (rather than splitting it onto another line), there is nothing here to recover it; the score-under-10,000 warning (above) remains the backstop for that case.
- **Chunk 2 (OCR) batch upload:** the entry form accepts any number of screenshots in one upload, not just the 1-2 for a single match. They're paired up by upload order (1st+2nd = match A, 3rd+4th = match B, ...) — there's no reorder UI, so the upload label spells out the required order (top screenshot then bottom, oldest match first). Each detected match renders as its own editable 15-row grid (the same review/edit step manual entry and single-match OCR already used) before saving, so a misordered pairing is caught by the developer, not silently saved. All matches in one batch share a single date/time field rather than per-match dates, since Score Info screenshots carry no timestamp the app could read and per-match date entry isn't worth the extra UI for the common case of logging several past matches at once. every new or changed function/module in `src/db/` and `src/ocr/` gets Vitest unit tests in the same change (see `CLAUDE.md`'s Working Agreement). Dexie-dependent code (`src/db/matches.js`) is tested against `fake-indexeddb` rather than a hand-rolled mock, so the real Dexie queries are exercised. `tesseractClient.js` is tested with `tesseract.js` mocked out (`vi.mock`), keeping the existing skipped smoke test as the only real-OCR check. React component tests (`RosterDashboard.jsx`, `MatchEntryForm.jsx`, etc.) are deferred until the UI stabilizes, since rewriting them alongside frequent UI changes isn't worth it yet. Coverage (`@vitest/coverage-v8`) is report-only via `npm run test:coverage`, with no enforced threshold. CI (`.github/workflows/test.yml`) runs lint + test on push/PR.
- **Chunk 2 (OCR) batch cross-match roster fallback [Developer]:** a batch upload's matches are assumed to share one identical 15-uma roster, including each uma's distance category — changing an uma's distance counts as replacing it for this feature's purposes, same framing as the delete/upgrade-nulls-history decision in `roadmap.md`. The Score Info screen's row order isn't assumed stable across matches (may be sorted by score), so matching is always by name, never by position. `applyBatchRosterFallback` (`src/ocr/parseScoreInfo.js`) runs once over the whole batch, in two passes: names are resolved first, by the same single-gap elimination `inferMissingDistances` already uses for distances, just applied to every match's confidently-read (exact-match) names instead of same-match distance-category counts; distances are then filled from a map built *after* those name fixes, so a row whose identity only became known through elimination can still supply its own distance to fill a different match's gap (the motivating case: match A misreads an uma's name but has its real distance, match B has the name right but is missing the distance — the two combine). Any OCR gap is filled using whatever any *other* match in the batch already resolved for the same uma, in either direction, not just from earlier uploads to later ones. A field OCR already resolved successfully (an exact-match name, or a non-null distance) is never overridden. If two matches confidently disagree on a uma's distance, neither value is used to fill anything and both matches get a warning naming the disagreement instead of a guess. No fuzzy/closest-match narrowing is used against the roster. There's no UI guard against a roster swap happening mid-batch; the existing editable/warned review table is relied on to catch it, and the upload control's label now discloses the assumption.
- **Chunk 2 (OCR) batch roster fallback, dropped-row case:** the same-gap elimination above also covers a row Tesseract dropped entirely (no name+points line recognized at all for that uma, not just a misread one left over to reassign) — real testing against the fixtures surfaced this as the more common failure than a misread name. When a match is unambiguously short exactly one known uma and has no leftover uncertain row to pin that gap on (as opposed to exactly one leftover row, which is the existing reassignment case), a new row is inserted for that uma with its distance filled in the same way as any other row, but points always left blank (`''`) — there's no OCR reading in that match to recover a real per-match score from, so it's the one field this fallback can never supply and the row's warning says so explicitly.
- **Chunk 2 (OCR) bare full-points split rescue:** re-testing the batch roster fallback against a real fixture pair (`Score_Info_7a/7b.jpg`) turned up the actual cause behind a "dropped" row (Maruzensky) that the batch fallback above couldn't fill in from other matches when the match was submitted alone: a third split-row shape, distinct from both the points-only/name-only rescue and the thousands-group prefix rescue already documented above. Real Tesseract output showed `"(<i 45,216 |"` (the whole comma-formatted score, in the points column, with no "pts" suffix at all) on one line and `"“2 Maruzensky ’ pts"` (the name, plus "pts", but zero digits) on the very next line — neither line matched `POINTS_REGEX` (one has no "pts", the other no digits), and the points line's token has a comma so it could never be mistaken for the bare 1-3 digit prefix case either. A PSM (page segmentation mode) change was tried first and rejected: forcing `PSM.SINGLE_COLUMN` on this same fixture does stop the split, but it also silently drops the distance-category word for nearly every other row on the screenshot (verified against the raw OCR text) — Tesseract's default `AUTO` column-aware layout analysis is what keeps the narrow distance column separate from the name/points column, so trading it away regresses far more than it fixes. Fixed instead at the same parse layer as the other two split variants: a bare comma-formatted token in the points column with no "pts" suffix (`BARE_POINTS_REGEX` in `parseScoreInfo.js`) is now treated as an orphan points value and paired by proximity with the nearest orphan name line, same mechanism as the points-only/name-only rescue. Verified against the real fixture: Maruzensky's row now reads correctly as `{ distance: 'Mile', points: 45216 }` with no manual entry needed.
- **Roster-first UI [Developer]:** the roster is now a stored, player-set list of 15 slots (`roster` table, Dexie schema v2) instead of being implied by whatever names were logged. On first open the player either types it in or picks "Auto-fill from screenshots", which opens the upload right away; the first match of that batch, after review, becomes the roster when saved, and every other match in the batch must have the same umas at the same distances. Scores (`matchEntries`) point at their slot by `rosterId`, not by name.
- **Deleting an uma's scores keeps its slot [Developer]:** "Delete scores" removes only that slot's scores; the name and distance stay. A slot can only be renamed or moved to another distance once it has no scores, so a slot's history always belongs to the name and distance it shows. To swap two umas' distances, delete both umas' scores, then edit both. A match left with no scores at all is removed too.
- **Undo a match [Developer]:** every logged match can be deleted (all of its scores) from the Match history list under the roster.
- **Schema v2 starts fresh [Developer]:** v1 match history had no roster to attach to, so the v2 upgrade clears `matches` and `matchEntries` rather than migrating them.
- **Match entry is roster-locked [Developer]:** once a roster exists, the entry modal (manual or screenshots) shows the 15 roster slots and only points are editable. OCR rows are matched to slots by name (`mapOcrRowsToRoster`); a roster uma OCR missed, an OCR uma not on the roster, or a distance disagreement becomes a warning, not a guess. Supersedes the "same `MatchEntryForm` 15-row grid" UX above: entry now happens in a modal (`MatchEntryModal`, native `<dialog>`), one page per match with Back/Next, opened from two small buttons below the roster. A batch still shares one date.
- **Roster view [Developer]:** a summary table (average, high, low, match count per uma) with rows that expand to show every score, plus a separate collapsible Match history list holding the delete-match buttons.
- The dev-only OCR debug panel was removed.
- **Reset roster [Developer]:** one button deletes the whole roster and every logged match and score, returning the app to the setup screen to start from scratch.
- **Sortable roster columns [Developer]:** every roster column header sorts the table; clicking a new column sorts it ascending, and clicking it again flips the direction (▲/▼ shown on the active column). Distance sorts by category order (Sprint → Dirt), not alphabetically. Umas with no scores stay at the bottom in either direction. Default: distance ascending.

## Open Questions

- Opponent Rating handling for players who don't always pick the Top Option (Advanced Mode currently assumes they do).
- How umas are identified from Edit Team/Race Results portraits — matching method against the uma database isn't decided.
- Whether scores are only meaningfully comparable within the same distance category (longer distances may have different base-point structures) — unconfirmed, flagged for further research.
- Middle and Bottom Option opponent ratings relative to the player's (only the Top Option is measured).
- Whether `I` and `T` need scaling to be comparable (currently added unscaled).
- How each uma's RANK badge (its Rating, needed for `T`) is captured: manual entry, or OCR/portrait matching on Score Info or Edit Team.
- How Advanced Mode treats matches logged in the MVP, which carry no Ace flags and no Team Rating or Support rate snapshots.
- More Top Option samples above 335,567 and between the sparse points from 65,493 to 181,639, to confirm the curve.
- Hosting platform: GitHub Pages, Vercel, or Netlify.
- Whether to self-host Tesseract.js's worker/wasm/lang-data assets (e.g. under `public/`) instead of relying on its jsDelivr CDN default — a deferred hardening item raised while building Chunk 2, not required to ship it.
- How these docs get updated now that they live in the repo (moved from a claude.ai Project into Claude Code).
- Now that per-uma Rating can be estimated from RANK badges via the floor table, should Phase 2 derive Team Rating from OCR'd badges instead of manual entry? (Revisits the manual-entry decision above.)
- The G rank's floor value (0) carried a footnote marker in the source with no footnote text provided — worth double-checking if a G-ranked uma ever needs to be distinguished from Rating 0 exactly.
